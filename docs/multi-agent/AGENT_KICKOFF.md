## 🎯 项目愿景

### 我们要解决什么问题？

**背景**:
- 全球数百万人接种了COVID-19疫苗
- 部分人报告了长期副作用（长新冠）
- 现有数据分散、难以理解
- 缺乏个性化风险评估工具

**我们的解决方案**:
1. **长新冠风险评估系统**
   - 输入批次号，获得风险评分
   - 个性化风险因素分析
   - 症状时间线预测

2. **症状模式识别系统**
   - 发现隐藏的症状组合
   - 识别患者亚群
   - 症状网络可视化

**成功的样子**:
- 10,000+ 月活跃用户
- 85%+ 风险预测准确率
- 被医学研究引用
- 帮助用户做出明智的健康决策

## 📋 开发原则

### 1. 用户至上
- 每个决策都问: "这对用户有价值吗?"
- 简单 > 复杂
- 快速反馈 > 完美设计

### 2. 数据驱动
- 用数据支持每个假设
- A/B测试重要决策
- 监控关键指标

### 3. 协作优先
- 早沟通、常沟通
- 代码审查是学习机会
- 尊重不同视角

### 4. 质量内建
- 测试不是事后补救
- 文档与代码同步更新
- 安全性从设计开始

### 5. 持续改进
- 每个Sprint都有Retrospective
- 勇于尝试新方法
- 从失败中学习

## 🔄 工作流程

### 典型的Feature开发流程

```
1. PM-Agent创建User Story
   ↓
2. Arch-Agent设计技术方案
   ↓
3. 开发Agent (BE/FE/DS)实现
   ↓ (并行)
4. QA-Agent编写测试
   ↓
5. Code Review (跨Agent)
   ↓
6. CI自动化测试
   ↓
7. Ops-Agent部署到Staging
   ↓
8. UAT (User Acceptance Testing)
   ↓
9. 部署到Production
   ↓
10. Doc-Agent更新文档
```

**下午 17:00-17:30 - 知识分享 (每周3次)**
- 技术分享

## 🚦 Git工作流

### 分支策略

```
main
  ├── develop
  │    ├── feature/us-001-risk-score
  │    ├── feature/us-002-personal-risk
  │    └── feature/ds-baseline-model
  └── hotfix/critical-bug
```

### 分支命名规范

- `feature/[issue-number]-[short-description]`
  - 例: `feature/us-001-risk-score`

- `bugfix/[issue-number]-[short-description]`
  - 例: `bugfix/123-fix-cache-invalidation`

- `hotfix/[short-description]`
  - 例: `hotfix/critical-security-patch`

### Commit消息规范

使用Conventional Commits:

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type**:
- `feat`: 新功能
- `fix`: Bug修复
- `docs`: 文档
- `style`: 格式
- `refactor`: 重构
- `test`: 测试
- `chore`: 构建/工具

**示例**:
```
feat(risk-api): add risk score calculation endpoint

Implement POST /api/v1/risk/score endpoint that calculates
long COVID risk score based on batch code and patient profile.

Closes #12
```

### PR (Pull Request) 流程

1. **创建PR**
   - 清晰的标题
   - 详细的描述
   - 链接相关Issue

2. **Request Review**
   - 至少1个其他Agent
   - Arch-Agent (如涉及架构)

3. **地址Review Comments**
   - 及时回复
   - 必要时讨论

4. **合并**
   - Squash commits (保持历史整洁)
   - 删除feature分支

**PR模板**:
```markdown
## What does this PR do?
Brief description

## Related Issues
Closes #123

## How to test?
1. Step 1
2. Step 2

## Checklist
- [ ] Tests added
- [ ] Documentation updated
- [ ] Code reviewed
```

## 🤝 协作礼仪

### Code Review礼仪

**作为Reviewer**:
- ✅ 积极: "很棒的实现! 建议..."
- ✅ 具体: "第42行可以优化成..."
- ✅ 建设性: "我们可以尝试..."
- ❌ 避免: "这代码太烂了"
- ❌ 避免: "显然你不懂..."

**作为Author**:
- ✅ 感谢反馈
- ✅ 解释设计决策
- ✅ 开放讨论
- ❌ 避免: 防御性
- ❌ 避免: 忽视建议

### 沟通最佳实践

1. **异步优先**
   - 使用GitHub Issues/PR comments
   - 详细描述问题
   - 不要期待立即回复

2. **同步必要时**
   - 复杂技术讨论
   - 紧急阻塞问题
   - Sprint规划会议

3. **@提及使用**
   - 需要特定Agent响应时使用
   - 紧急问题使用
   - 不要过度使用

## ❓ 常见问题

**Q: 我该从哪里开始?**
A: 首先阅读PRD，然后查看SPRINT_1_TASKS找到你的任务。
